  Root cause: a real bug in the ROMS source

  Your ININAME file (initial_1993-12-31.nc) has ocean_time = 385692, units
  "hours since 1950-01-01 00:00:00" — which correctly corresponds to 1993-12-31 
  12:00, matching the filename.

  The bug is in ROMS/Utility/get_state.F (~line 392-406), where the code that
  converts the input time to seconds only recognizes 'day' and 'second' in the
  units string:

  IF (INDEX(TRIM(var_Achar(i)),'day').ne.0) THEN
    time_scale=day2sec
  ELSE IF (INDEX(TRIM(var_Achar(i)),'second').ne.0) THEN
    time_scale=1.0_dp
  END IF

  It's missing the 'hour' case. Compare with the correct version of this same
  logic in check_multifile.F (~line 706-712), which is why your boundary-file
  date range printed correctly:

  IF (INDEX(TRIM(var_Achar(i)),'day').ne.0) THEN
    Tscale=86400.0_r8
  ELSE IF (INDEX(TRIM(var_Achar(i)),'hour').ne.0) THEN
    Tscale=3600.0_r8
  ELSE IF (INDEX(TRIM(var_Achar(i)),'second').ne.0) THEN
    Tscale=1.0_r8
  END IF

  Because get_state.F silently skips scaling for "hours since ...", the value
  stays in hours but gets used as if it were seconds. That's exactly why the
  reported init time (1975-01-02 22:15:48, i.e. TIME_REF + 166548 "seconds") is
  off by a factor of 3600/86400 = 24× from the correct 1993-12-31 — I verified
  the arithmetic matches exactly.

  Two ways to fix it

  Option A (no recompile, fastest): rescale the time units in your
  initial-conditions file so it isn't "hours since ...":
  ncap2 -O -s 'ocean_time=ocean_time*3600.0' initial_1993-12-31.nc
  initial_1993-12-31_fixed.nc
  ncatted -a units,ocean_time,o,c,"seconds since 1950-01-01 00:00:00"
  initial_1993-12-31_fixed.nc
  Then point ININAME in roms_cb600m.in at the fixed file. (Worth fixing your
  Matlab c_initial script too, so future init files use "seconds since ..."
  instead of "hours since ...".)

  Option B (proper fix, needs recompile): add the missing 'hour' branch to
  get_state.F (mirroring check_multifile.F) and rebuild romsM.

  I'd suggest Option A to unblock this run today, and separately patching
  get_state.F since any other ROMS input file using "hours since ..." as its
  initial-condition source will hit the same bug. Want me to apply the source
  patch and/or regenerate the fixed NetCDF file now?

● Progress — DSTART fix worked (step counter is now sane: 720, i.e. ntstart=721,
  matching 12 hours into 1994-01-01). But it exposed a genuine edge case in the
  QUICKSAVE multi-file scheduling logic in output.F.

  The math: ntstart-1 = 720. With NDEFQCK=1440, ROMS computes:
  idefQCK = ((ntstart-1)/ndefQCK)*ndefQCK   ! = (720/1440)*1440 = 0   (integer 
  division)
  IF (idefQCK < iic-1) idefQCK = idefQCK + ndefQCK   ! 0 < 720, so idefQCK = 
  1440
  So the code decides the next file boundary is at step 1440 and skips creating
  the QUICKSAVE file now. But the separate write-trigger check only tests
  MOD(iic-1, NQCK) == 0 — and 720 mod 180 = 0, so it tries to write anyway, into
  a file that was never defined → same NC_EBADID crash.

  This only bites QCK because NQCK (180) ≠ NDEFQCK (1440) and your run's start
  offset (720) happens to be a multiple of NQCK but not of NDEFQCK. HIS avoided
  this because NDEFHIS=0 uses a simpler "always define at ntstart" path. AVG/DIA
  are actually safe too — NAVG=NDEFAVG=1440 and NDIA=NDEFDIA=1440, so their
  write and define steps coincide.

  Cleanest fix, no recompile: set NDEFQCK = 0 so QUICKSAVE uses that same simple
  "one file, defined at ntstart" path instead of the multi-file boundary
  arithmetic — matching what your .in file's own documentation says ("NDEFQCK=0,
  the model will only process one QUICKSAVE file"), and your 29-day run isn't
  long enough that a single QCK file would be unreasonably large anyway.
